# Stats: log magnitudes and see them over time

## What is being added

A `stats` command records a number against a declared stat, such as push-ups,
steps, kilometres run or money spent, and shows how that number moves over
time.

    stats new pushups --thread Processes/Wellness --type int --agg sum
    stats log pushups 25
    stats series pushups --since 2026-09-01 --by week

The reason: some things are best tracked as a magnitude, not as text. A
command per thing (`pushups`, `pullups`) does not scale. One command over
declared stats does.

## Declaring a stat

A stat is declared in its thread's frontmatter, beside `cadences`:

```yaml
stats:
  - name: pushups
    type: int
    agg: sum
  - name: steps
    type: int
    agg: last
```

Block style, as `cadences` are written: the frontmatter reader takes a list
of mappings in that form only, not one-line `{name: ...}` items.

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | Lowercase letters, digits and `-`. Unique across the vault. |
| `type` | yes | `int` or `decimal` |
| `agg` | yes | How `series` combines several entries in one period: `sum`, `last` or `max` |

- **One stat, one thread.** Because names are unique across the vault,
  `stats log` finds the thread from the name. You never type the thread.
- **No unit.** If a stat's name alone is unclear, put the unit in the name
  (`run-km`, `spend-zar`).
- **No bool type.** For an event, log `1` each time it happens (see
  [Recording an event](#recording-an-event)).
- `agg` matters when a period holds more than one entry. Push-ups logged
  in sets of 20, 25 and 15 give 60 under `sum`. Step counts of 3,200 and
  8,900 give 8,900 under `last`. Pull-up sets of 8, 10 and 7 give 10
  under `max`.

`stats new` writes the declaration into the thread's frontmatter: it
appends to an existing `stats:` list, or adds the key before the closing
`---`. A `stats:` that is not a block list (`stats: []`) is refused; edit it
by hand. Renaming a
stat, or changing its type or agg, means editing the frontmatter by hand. Old
entries are not rewritten, and if a hand edit breaks something, that is the
editor's responsibility.

## Recording an entry

`stats log <name> <value>` buffers a line like the other `add-*` captures:

    - [[Processes/Wellness]] STAT: pushups 25 <!--2026-10-07T07:42:10-->

The thread link comes first, as on every other buffer line.

`buffer flush` files it in the thread's daily log. Unlike other lines, it
keeps the timestamp:

    STAT: pushups 25 <!--2026-10-07T07:42:10-->

In Obsidian's reading view this shows as `STAT: pushups 25`.

- The timestamp is the buffer's: local time, `YYYY-MM-DDTHH:MM:SS`.
- `-d, --date <YYYY-MM-DD>` and `-t, --time <HH:MM>` backdate the entry,
  as `hours log` does. The default is now.
- The value must parse as the stat's type. An `int` stat rejects `2.5`.
- Negative values and zero are allowed.
- An unknown name exits `1` and lists the close matches. There is no fuzzy
  auto-pick, because a wrong guess would silently file the entry under the
  wrong stat.
- A mistake is fixed with `buffer rm` before flush, or by editing the log
  by hand after it. Entries have no id.

## Recording an event

Something that happens or doesn't, like "I drank alcohol today", is an `int`
stat logged as `1` each time it happens:

    stats new alcohol --thread Processes/Wellness --type int --agg sum
    stats log alcohol 1

Under `sum`, the series counts occurrences per period. Use `--agg max` if you
only want "did it happen at all" (1 or 0).

This convention must be stated in `stats --help`, `stats log --help` and the
manual, so that an assistant reading the tool definitions knows how to record
an event. Updating the agent's skill and tool definitions is a separate story.

## Viewing

| Subcommand | What it does |
|---|---|
| `list` | Lists declared stats: name, thread, type, agg. `--json`. |
| `series <name>` | One row per period: the period and the aggregated value. `--since`, `--until`, `--by day\|week\|month` (default `day`), `--json`. |

- `series` reads the thread's logs and the unflushed `STAT:` lines in the
  buffer, so today's entries show before a flush. The buffer parser
  already exists (`parse_buffer_entries`), so this is a filter on its
  output, not new parsing.
- Every period in the range is listed. A period with no entries shows `-`
  (`null` in JSON), not `0`. A gap is a day with nothing logged, which is not
  the same as a logged zero.
- A week starts on Monday. A week is labelled by its Monday, a month as
  `YYYY-MM`.
- With no `--since` the series starts at the first value; with no
  `--until` it ends today, or at the last value if that is later.
- A value that does not read as the stat's type stops `series`, naming the
  file and line. It is not skipped: a wrong total is worse than none.
- `search` counts `STAT:` lines as log entries, and `search stream` shows
  them, with their clock time, before and after flush alike.

## Lint

- The `thread` schema gains `stats`, validated like `cadences`, plus a
  vault-wide check that names are unique.
- A new line schema, `stat_line`, checks `STAT:` lines. Each must be in a
  log, name a stat declared on the log's own thread, carry a value of that
  stat's type, and carry a timestamp whose date is the log's date.
- `buffer tend` validates `STAT:` lines the same way.

**Cost:** small. Lint already reads every log file and matches task anchors
line by line. This adds one regex per log line and one dict lookup against
the declared stats. The declarations are read by a second pass over the
thread files, once per run and only when a log holds a STAT line; lint's
own reading of the thread files is not reused. On the production vault, lint
went from 0.28s to 0.31s.

## Touch points

`stats` command (new module), shared stat helpers in `vault.py`, buffer
(new line kind, keep timestamp on flush), lint and the `thread`, `log` and
new `stat_line` schemas, `search` (count and stream STAT lines), MANUAL.md
and `dev/tools/` (regenerated).

## Done when

- `stats new`, `list`, `log` and `series` behave as above, with tests for
  each `agg`, for gaps, and for the buffer being included before a flush.
- An event stat (`alcohol`, logged as `1`) produces a correct per-day count
  and a correct per-week count.
- `lint` flags an undeclared stat, a wrong-typed value, a duplicate stat name
  across threads and a timestamp off the log's date. A clean vault still
  passes.
- The event convention appears in `stats --help`, `stats log --help` and
  MANUAL.md.

## 1. A stats list the reader cannot see

**The bug:** a flush-left item under `stats:` is valid YAML, but neither
frontmatter reader takes it. `stats list` showed nothing, `lint` was clean,
and `stats new` wrote its item above the hidden one. The same gap existed
for `cadences:`.

**Decision: report it and refuse it; do not teach the readers flush-left
lists.** Two readers would have to change in step, for a form no tool
writes and no file in the production vault uses (469 thread and person
files checked).

- `vault.unread_lines` finds a frontmatter line the reader takes as nothing:
  not blank, not a `#` comment, not indented, not `key: value`.
- `lint` reports each one, for any key:
  `frontmatter line is not read: '- name: steps'; indent list items under their key`.
- `stats new` refuses a thread file with such a line, and writes nothing:
  `frontmatter line 7 is not read ('- name: steps'); indent it under its key first (`lint` reports it)`.

**Tests:** `test_a_flush_left_list_item_in_frontmatter_is_reported[stats|cadences]`
and `test_new_refuses_a_stats_list_it_cannot_read`.

## 2. Spec changes made during the build

**Approved by Riaz on 2026-10-07.** These were decided while building, not
agreed beforehand:

1. STAT lines are checked by a new line schema, `stat_line`, rather than
   by rules added to the `log` schema. The `log` schema lists STAT among
   its body lines and points at `stat_line`.
2. Declarations are written in block style. The one-line
   `{name: ..., type: ..., agg: ...}` form is not read, because the
   frontmatter reader does not support it. The `run-km` and `alcohol`
   examples were dropped from the YAML block; `alcohol` is still in
   "Recording an event".
3. `stats new` refuses a `stats:` that is not a block list (`stats: []`).
4. A logged value of the wrong type stops `series`, naming the file and
   line, rather than being skipped.
5. Without `--since`, a series starts at the first value. Without
   `--until`, it ends today, or at the last value if that is later.
6. A week is labelled by its Monday, a month as `YYYY-MM`.
7. `search` changed after all: it counts STAT lines and streams them after a
   flush. Before, a stat showed in the stream while buffered and dropped out
   once flushed.

## 3. The buffer line in the story

Corrected to `- [[Processes/Wellness]] STAT: pushups 25 <!--…-->`, the
format the code writes, with the thread link first as on every buffer line.

## 4. Exit codes in the tool definition

The harvest finds exit codes from literal `die()` calls in the tool's
module. The common errors are raised as `ValueError` in `vault.py` and reach
`die` as `str(e)`, so the model never saw them. The `stats` docstring now
lists every exit-1 case, and the exit-2 usage errors. The harvest passes it on
as the author's intent. `dev/tools/stats.json` and MANUAL.md were
regenerated.

## 5. A name repeated on one thread

`find_stat` now says `stat 'steps' is declared twice on Processes/Wellness;
`lint` reports it, and one must be removed`. `stats new` names each thread
once.

**Test:** `test_log_names_a_stat_declared_twice_on_one_thread`.

## 6. Decimal precision in JSON

**Not changed; agreed with Riaz on 2026-10-07.** A JSON number goes through a float,
which is exact to 15 significant digits. That covers any realistic
measure, and the text output is exact. Writing exact numbers would need
either strings, which changes the type an agent reads, or hand-built JSON.
Left as it is.

## 7. The Cost claim

Reworded. The declarations are read by a second pass over the thread files,
once per run and only when a log holds a STAT line. Lint's own reading of
the thread files is not reused.

## 8. Rules written in two places

Noted; not changed. The `stat_line` schema's shape and constraints repeat
`vault.STAT_LINE_RE` and the name and value rules, as `task_anchor` does.
Lint applies both, so a drift between them shows up as a lint violation on
a line the CLI wrote.
